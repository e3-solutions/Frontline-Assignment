# Voice-agent evaluation design

## Purpose and priority

The agent makes decisions from a live PSTN transcript.  A wrong carrier MC can
associate a call with the wrong company, while slow turn handling makes the
phone experience unusable.  The first evaluation slice therefore measures
transcription fidelity, MC extraction fidelity, and their latency separately.
It does not claim to validate a live carrier provider, a real phone call, or an
LLM's nondeterministic negotiation behavior.

## External corpus: Spirelight

Spirelight's licensed English (US) conversational corpus is the chosen
external evaluation source because it supplies unscripted dual-channel audio,
time-aligned human-verified transcripts, speaker metadata, and consent
records.  It is not included in this repository: the data is licensed and the
repository must remain safe to run without credentials or restricted data.

After procurement, a data steward must create a manifest outside Git with one
record per caller turn:

```json
{
  "id": "licensed-case-001",
  "audio_path": "/restricted/spirelight/case-001.wav",
  "reference_transcript": "my MC number is 123456",
  "observed_transcript": "my MC number is 123456",
  "expected_mc": "123456",
  "observed_mc": "123456",
  "stt_latency_ms": 420
}
```

Select a fixed, versioned holdout before measuring.  Stratify it by 8 kHz
telephony simulation, accent/region, background noise, interruptions, spoken
digits, company names, prices, and load references.  Do not use raw licensed
audio or identifiers in CI output.

## Metrics and decision rule

- **WER:** token Levenshtein distance divided by reference-token count.
- **MC EER:** the fraction of MC-bearing cases whose final selected MC is
  missing or differs after digit-only normalization.
- **p50/p95 latency:** captured at the STT callback and each tool boundary;
  reported separately rather than folded into accuracy.
- **Positive quality score:**
  `H(max(0, 1 - mean_WER), 1 - MC_EER)`.

The harmonic mean is appropriate because it prevents a strong general
transcript score from concealing weak MC extraction.  It is a positive score
where 1 is best.  Its complement (`1 - score`) is an error score, not a
positive score.  A release gate should require the individual metrics as well;
the composite is only a summary and cannot permit a high MC EER.

Initial proposed gates, to be calibrated on a signed-off holdout:

| Metric | Proposed gate |
| --- | ---: |
| MC EER | <= 1% |
| Unsafe false verification rate | 0% |
| Mean WER | <= 15% |
| STT p95 latency | <= 1.5 s |
| Composite quality score | >= 0.92 |

## Running the offline harness

Use the [ASR and carrier-MC metric runbook](ASR_EVALUATION_RUNBOOK.md) for the
full replication procedure. The checked-in fixture is synthetic and proves
metric behavior only:

```bash
python3 -m unittest discover -s evaluations/tests -v
python3 -m evaluations.run_asr_eval
```

To evaluate a licensed manifest whose `observed_*` fields were generated by an
approved credentialed Deepgram run, use:

```bash
python -m evaluations.run_asr_eval --cases /restricted/spirelight/cases.json \
  --output evaluation-results.json
```

The runner makes no network call and does not transmit audio.  A future
credentialed adapter may generate `observed_transcript`, but must remain an
explicit opt-in integration job.
